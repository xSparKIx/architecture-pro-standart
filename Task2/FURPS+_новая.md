| Код | Требование | Комментарий |
|-----|------------|-------------|
|F   |Функциональные требования (Functionality)|
|F1|Клиенты должны иметь возможность подавать заявки на депозиты и кредиты через интернет-банк и сайт.|Базовый функционал MVP.|
|F2| Для новых клиентов на сайте: отображение списка депозитов/кредитов, прием ФИО и номера телефона. |Первый шаг воронки для неидентифицированных пользователей.|
|F3| Для существующих клиентов в интернет-банке: отображение персонализированных ставок по депозитам и предодобренных кредитных предложений.|Повышение конверсии за счет персонального подхода.|
|F4| Интеграция с колл-центром: заявки с сайта должны автоматически поступать в систему колл-центра для обработки менеджером. |Обеспечение непрерывности клиентского journey.|
|F5| Подтверждение операций (открытие депозита, подача заявки на кредит) через SMS-код.| Требование безопасности и подтверждения намерений (2FA).|
|F6| Арх. значимое: Создание централизованного, доступного через API, сервиса управления ставками (депозиты и кредиты). Он должен заменить Excel-файлы. |Критично для устранения ручных процессов, обеспечения консистентности данных и их доступности для всех каналов (сайт, ИБ, АБС).|
|F7| Арх. значимое: Интеграция с системой скоринга (для кредитов) для получения предварительного решения онлайн (на сайте, при указании паспортных данных). |Ключевая функция для автоматизации кредитного процесса.|
|F8| Арх. значимое: Механизм отслеживания статуса заявки (как для депозита, так и для кредита) и информирования клиента via SMS на ключевых этапах (получение, одобрение, отказ, необходимость визита). |Повышение прозрачности процесса для клиента.|
|F9| Для кредитов: возможность "продолжения" заявки, созданной на сайте, когда клиент приходит в отделение (и наоборот). | Избежание дублирования заявок и улучшение клиентского опыта.|
|U| Удобство использования (Usability)||
|U1| Интерфейсы сайта и интернет-банка должны соответствовать утвержденной в компании системе дизайна (brand guidelines). | Обеспечение единого узнаваемого стиля и удобства для пользователя.|
|U2| Отклик интерфейса (UI) на любые действия пользователя должен быть максимально быстрым (< 200-300 мс).|Прямое требование бизнеса к качеству пользовательского опыта.|
|U3| Процесс подачи заявки должен быть максимально упрощен и содержать минимальное количество шагов. |Увеличение конверсии.|
|R| Надёжность (Reliability)||
|R1| Арх. значимое: Общая доступность (availability) всех систем, участвующих в процессе (ИБ, сайт, сервисы), должна составлять 99.9%.|Прямое бизнес-требование.|
|R2| Арх. значимое: Необходимо обеспечить отказоустойчивость и возможность работы в режиме Active-Active или Active-Standby между двумя ЦОД. |Требование вызвано текущей уязвимостью (все в одном ЦОД).|
|R3| Арх. значимое: Система должна обрабатывать пиковые нагрузки без потери функциональности. Необходимо предусмотреть горизонтальное масштабирование веб-сервисов и приложений.|Требование к масштабируемости, основанное на ограничениях АБС.|
|R4| Механизмы шифрования трафика (TLS) и данных должны быть устойчивы к сбоям и не снижать общую доступность системы.|Базовое требование безопасности.|
|P| Производительность (Performance)||
|P1| Арх. значимое: Время отклика (response time) для любой операции в интернет-банке и на сайте должно измеряться в миллисекундах.|Прямое требование бизнеса, основанное на текущих проблемах (загрузка справочников >1 сек).|
|P2| Арх. значимое: Обмен данными с системой скоринга (для кредитов) должен происходить в режиме, близком к реальному времени (десятки-сотни мс), чтобы не задерживать выдачу решения.|Критично для пользовательского опыта при онлайн-одобрении.|
|P3| Арх. значимое: Загрузка справочной информации (списки продуктов, тарифы) должна быть кэширована для обеспечения требуемой производительности.|Решение текущей проблемы с медленной загрузкой.|
|S| Поддерживаемость (Supportability)||
|S1| Арх. значимое: Для новых разработок максимально использовать уже существующие в банке технологии: MS SQL, Oracle, знакомые языки программирования. | Снижение cost of ownership и рисков, связанных с обучением.
|S2| Арх. значимое: Предусмотреть разработку полной технической документации на все компоненты системы. |Требование для будущего расширения и поддержки.|
|S3| По возможности избегать доработок ядра АБС силами подрядчика. Реализовывать новую функциональность в отдельных сервисах.|Снижение рисков, стоимости и времени разработки.|
|+R| Ограничения (Restrictions)||
|R+1| Арх. значимое: Новая архитектура должна минимизировать прямые онлайн-обращения к АБС из интернет-банка и сайта из-за риска перегрузки её БД. |Критическое ограничение, накладываемое командой АБС.|
|R+2| Арх. значимое: База данных АБС масштабируется только вертикально.|Важное технологическое ограничение, влияющее на архитектуру решений.|
|R+3| Текущая версия платформы интернет-банка несовместима с Apache Kafka.|Ограничение, которое может повлиять на выбор технологий очередей.|
|R+4| Не нагружать систему скоринга дополнительными процессами предрасчетов. Она испытывает пиковые нагрузки в рабочее время.|Ограничение, влияющее на дизайн кредитного процесса (кэширование предодобренных предложений?).|
|R+5| Обмен данными между АБС и Кредитным конвейером в текущей реализации происходит раз в сутки, и участить его невозможно.|Существующее ограничение, которое нужно обойти для ускорения обработки кредитных заявок в MVP.|
|R+6| Все передаваемые данные (особенно чувствительные с сайта) должны быть защищены механизмами шифрования (TLS).|Юридическое и регуляторное ограничение.|
|R+7| Новые клиенты не могут быть полностью onboarded онлайн. Требуется личный визит в отделение для идентификации.|Регуляторное ограничение (Закон "О ПОД/ФТ").|
