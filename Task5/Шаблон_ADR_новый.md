### <a name="_qmphm5d6rvi3"></a>**Решение**
Приведите диаграммы контекста и контейнеров в модели C4. Опишите там основные компоненты и интеграции всех элементов решения.

Также опишите, какой логикой вы руководствовались в ходе принятия решений и выбора технологий. Не забывайте, что необходимо учесть все функциональные и нефункциональные требования.

#### Логика принятия архитектурных решений:

1. Синхронная REST-архитектура - Прямые вызовы между сервисами без брокера сообщений, упрощение архитектуры
2. Кэширование предодобренных предложений - Снижение нагрузки на скоринг и БКИ, улучшение производительности (NFR-1)
3. Единый сервис заявок как оркестратор - Централизованное управление процессом кредитования и координация между системами (ASR-3)
4. Circuit breaker pattern для БКИ - Обеспечение отказоустойчивости при недоступности внешних систем (NFR-10)
5. BPMN для управления процессами - Гибкость в изменении бизнес-процессов без переписывания кода (UC-5)
6. Балансировщик нагрузки для БКИ - Роутинг запросов между разными бюро кредитных историй (NFR-3)

#### Технологический выбор:

* Кэш: Redis Cluster - высокая производительность, репликация, persistence
* База заявок: PostgreSQL - поддержка JSON, транзакции, ссылочная целостность
* API Gateway: Kong - уже используется в банке, плагинная архитектура
* BPMN движок: Camunda - открытая платформа, мощные возможности orchestration
* Сервис скоринга: Python - богатая экосистема для ML и аналитики
* Основные сервисы: Java Spring - совместимость с enterprise-стеком банка

Балансировщик БКИ: Nginx - роутинг и failover между разными провайдерами

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Опишите здесь наиболее важные альтернативные решения.

#### Альтернатива 1: Асинхронная архитектура с брокером сообщений

* Недостатки: Усложнение архитектуры, дополнительные точки отказа
* Ограничения: Требует обучения команд, увеличивает операционные затраты
* Риски: Нарушение условий задачи, которая запрещает использование брокера сообщений

#### Альтернатива 2: Прямая синхронная интеграция с АБС

* Недостатки: Высокий риск перегрузки АБС, нарушение NFR-7
* Ограничения: Низкая производительность при пиковых нагрузках
* Риски: Падение основной банковской системы

#### Альтернатива 3: Ежедневный batch-скоринг

* Недостатки: Неактуальные данные, ухудшение клиентского опыта
* Ограничения: Не позволяет использовать текущие данные клиента
* Риски: Выдача кредитов на основе устаревшей информации

**Недостатки, ограничения, риски**

Подробно опишите здесь недостатки, ограничения и риски выбранного решения.

1. Прямая связность сервисов: Удаление брокера сообщений увеличивает связь между компонентами
2. Каскадные сбои: Отказ одного сервиса может повлиять на доступность других
3. Сложность балансировки нагрузки: Требуется проработанная архитектура с учетом всех возможных проблем для обработки пиковых нагрузок
4. Ограниченная отказоустойчивость: Без асинхронной буферизации сложнее справляться с временной недоступностью сервисов
5. Синхронные вызовы к БКИ: Могут создавать узкое место при высокой нагрузке
6. Сложность отслеживания транзакций: Распределенная трассировка становится критичной
7. Ограниченная масштабируемость: Вертикальное масштабирование может быть дороже горизонтального
