#### Логика принятия архитектурных решений:

1. Буферный слой (Сервисы Интернет-банка) между фронтендом и АБС - решает ключевую проблему ограничения нагрузки на АБС (NFR-5) и обеспечивает ее изоляцию. Все внешние запросы принимают на себя сервисы Интернет-банка.
2. Асинхронная коммуникация через брокер сообщений Kafka - обеспечивает надежность, масштабируемость (NFR-3) и отказоустойчивость (NFR-7). Позволяет системам работать независимо и обрабатывать пиковые нагрузки.
3. Выделенные BFF (Backend For Frontend) для Web и Mobile - обеспечивают оптимальный формат данных для каждого клиента, повышая производительность (NFR-2) и упрощая развитие клиентских приложений.
4. Кэширование справочников и сессий в Redis - решает проблему медленной загрузки данных и повышает отзывчивость интерфейсов (NFR-2).
5. Микросервисная архитектура для новых компонентов - обеспечивает гибкость, независимость разработки и масштабируемость (NFR-3).
6. Все внешние интеграции (БКИ, СМС) возложены на сервисы Интернет-банка - обеспечивает изоляцию АБС и безопасность (NFR-8). АБС общается только с внутренней шиной данных (Kafka).
7. Двухканальное распространение данных: Для внутренних систем используется высокоскоростной асинхронный канал (Kafka), для внешних партнеров - надежный файловый обмен через SFTP. Это обеспечивает баланс между производительностью и безопасностью (NFR-10, NFR-11).
8. Единый источник истины: Сервис депозитов АБС остается единственным источником актуальных ставок. Все системы получают данные из одного источника, что гарантирует консистентность.
9. Изоляция внешних партнеров: Партнерские кол-центры не имеют прямого доступа к внутренним системам банка. Обмен происходит только через безопасный SFTP-канал, что соответствует принципам безопасности (NFR-11).
10. Гибкость интеграции: Использование стандартных форматов (JSON/CSV) позволяет легко интегрироваться с различными партнерскими системами без необходимости разработки сложных API (NFR-14).

#### Технологический выбор:

* Брокер сообщений: Apache Kafka - выбран за высокую пропускную способность, надежность и возможность повторной обработки сообщений.
* Кэш: Redis - высокая производительность и низкая задержка, идеален для кэширования и хранения сессий.
* Базы данных: PostgreSQL - для обеих систем (Интернет-банк и АБС) выбрана одна SQL-СУБД для унификации, обладает хорошей производительностью и надежностью.
* Бэкенд: Использование существующих компетенций в банке (NFR-6).
* Фронтенд: JavaScript, React - современный стек для построения динамических интерфейсов.
* SFTP-сервер: OpenSSH SFTP server - стандартное, безопасное и надежное решение для файлового обмена.
* Формат данных: JSON/CSV с цифровой подписью - обеспечивает простоту обработки и проверку целостности данных.
* Шифрование: GPG/OpenSSL - для шифрования файлов перед отправкой партнерам.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Опишите здесь наиболее важные альтернативные решения.

#### Альтернатива 1: Прямая синхронная интеграция с АБС (REST/API)

* Недостатки: Высокий риск перегрузки и недоступности АБС, нарушение требования NFR-5 и NFR-7.
* Ограничения: Невозможность горизонтального масштабирования точки входа в АБС.
* Риски: Падение основной банковской системы при пиковых нагрузках из цифровых каналов.

#### Альтернатива 2: Использование RabbitMQ вместо Kafka

* Недостатки: Менее отказоустойчивая модель потребления сообщений (после обработки сообщение удаляется). Сложнее масштабировать.
* Ограничения: Меньшая пропускная способность по сравнению с Kafka при большом объеме сообщений.
* Риски: Возможность потери сообщений при определенных сценариях сбоя потребителя.

#### Альтернатива 3: Полная миграция на микросервисную архитектуру

* Недостатки: Высокая сложность реализации, требует полной переработки АБС.
* Ограничения: Затягивание сроков вывода продукта на рынок.
* Риски: Высокая стоимость и риск неудачи проекта.

#### Альтернатива 4: Прямой API-доступ для партнеров

* Недостатки: Требует разработки и поддержки сложного API, создает риски безопасности при прямом доступе к системам банка.
* Ограничения: Партнерские системы могут не поддерживать необходимые протоколы аутентификации.
* Риски: Возможность DDoS-атак через публичный API, сложность управления доступом.

#### Альтернатива 5: Использование email для рассылки ставок

* Недостатки: Низкая надежность доставки, ограничения на размер файлов, проблемы с безопасностью.
* Ограничения: Отсутствие гарантированной доставки, сложность автоматической обработки.
* Риски: Возможность перехвата конфиденциальной информации.

### **Недостатки, ограничения, риски**

Подробно опишите здесь недостатки, ограничения и риски выбранного решения.

1. Сложность синхронизации данных между БД Интернет-банка и АБС из-за асинхронной коммуникации.
2. Задержка в обновлении данных: Клиенты могут видеть не самое актуальное состояние заявки в течение короткого промежутка времени.
3. Операционная сложность: Дополнительная инфраструктура (Kafka, Redis) требует поддержки, мониторинга и глубоких знаний.
4. Ограниченная функциональность MVP: Некоторые процессы могут быть упрощены в первой версии.
5. Риск несогласованности данных: При неправильной настройке или сбое Kafka возможна потеря или дублирование сообщений. Необходима тщательная настройка идемпотентности потребителей.
6. Кривая обучения: Необходимость обучения команд работе с новой архитектурой и технологиями, в частности, с паттернами асинхронного взаимодействия.
7. Отладка: Трассировка запроса, который проходит через несколько сервисов и асинхронную шину, сложнее, чем трассировка монолитного синхронного приложения.
8. Задержка распространения данных: Файловый обмен через SFTP может добавлять задержку до 15 минут против обновления real-time в Kafka.
9. Сложность обработки ошибок: Необходимость механизма повторной отправки файлов при сбоях на стороне партнера.
10. Версионность форматов: Изменение формата файлов требует координации со всеми партнерами.
11. Мониторинг доставки: Необходимость дополнительного мониторинга процесса выгрузки/загрузки файлов.
12. Ручное вмешательство: Возможность необходимости ручного вмешательства при сбоях в файловом обмене.
13. Хранение credentials: Безопасное хранение и ротация SSH-ключей для доступа к SFTP.
14. Пропускная способность SFTP: Ограничения на одновременное количество подключений и скорость передачи данных.
